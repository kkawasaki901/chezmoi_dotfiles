# Book Research

大きなテーマについて、「一通り網羅した分厚い本」を執筆するつもりで調査・整理する。最初に体系的な目次を確定し、各節を独立したMarkdown文書として順に執筆する。作業状態は常にディスク上に保存し、別セッションでも再開可能にする。

## 1. 作業場所と成果物

- ユーザーが出力先を指定していればそこを使う。指定がなければカレントディレクトリの `research/<theme-slug>/` を使う。
- 既存ファイルを調べてから作業する。過去の調査内容を無断で初期化・上書きしない。
- 生成する基本構成は次のとおり。`chapters/` 以下は目次に応じて増やす。

```text
research/<theme-slug>/
├── index.md           # 読み始める場所、テーマ・スコープ・文書への導線
├── outline.md         # 全体目次（章・節の正本）
├── progress.md        # チェックリスト、作業位置、再開メモ
├── sources.md         # 出典台帳
└── chapters/
    ├── 01/
    │   ├── 01-01.md   # 第1章第1節
    │   └── 01-02.md
    └── 02/
        └── 02-01.md
```

- 原則として **1つの節（例: 2.3）につき1つのMarkdownファイル** を作る。節内の小項目（例: 2.3.1）はそのファイルの見出しにする。独立した大きな論点は別の節に分割する。
- ファイル名と節IDを対応させ、IDは可能な限り固定する。目次修正時も執筆済みファイルとの対応を壊さない。
- Markdownの相対リンクを使う。未作成ファイルへのリンクを完成済み文書として提示しない。

## 2. 作業開始・再開の判定（毎回最初に行う）

1. 対象テーマと出力先を確認する。ユーザー指定がなくても合理的なスコープ・想定読者を仮置きして着手してよい。
2. 出力先に `progress.md`、`outline.md`、`index.md`、`sources.md`、`chapters/` が存在するか確認する。
3. 既存プロジェクトなら `progress.md` → `outline.md` → 該当する節の実ファイル → `sources.md` を読み、チェック状態と実態を照合する。
4. 矛盾していたら実ファイルを確認して `progress.md` を修正する。「完了」と書いてあっても本文が未完成なら未完了に戻す。既存の執筆内容は保持する。
5. `progress.md` の「次の具体的な作業」から再開する。メモが古ければ、未完了の節・要検証箇所から次の作業を選ぶ。
6. 新規プロジェクトの場合は、以下の「全体設計」から始める。

会話履歴や内部の記憶に依存せず、**ファイルだけで作業状態を復元できること** を優先する。

## 3. 全体設計：本文より先に目次を作成する

1. テーマの範囲、想定読者、前提知識、対象地域・年代、調査の基準日、扱わない範囲を `index.md` に記載する。
2. テーマ全体を俯瞰し、専門書・体系的教科書の目次を作るつもりで `outline.md` を作成する。必要に応じて概説資料や代表的文献を確認し、一般に認められている分類・論点を把握する。
3. 大分類（部・章）→ 中分類（節）→ 小項目（節内見出し）という階層にする。概念、原理、構成要素、分類、歴史、方法論、応用、実証、論争・限界、最新の動向など、**テーマに関連する軸** を漏れなく点検する。ただし無関係な章を数合わせで設けない。
4. 初学者が基礎から読み進められ、専門的な論点へ段階的に進める順序にする。前提関係・対立する見解・隣接分野との境界も整理する。
5. 似た節の重複、重要な空白、粒度の極端なばらつき、前提知識の欠落を点検する。必要なら目次を改訂する。
6. **本格的な節の執筆に入る前に**、全節のID、名称、予定ファイルパスを `progress.md` にチェックリスト化する。
7. 完了した本文がある状態で目次を改訂する場合は、節の追加・統合・移動と理由を `progress.md` の変更履歴に残し、リンクと完了状態を更新する。

「網羅性」は単に項目数が多いことではない。重要な主題・代表的な異説・前提となる概念が体系的に位置付けられている状態を目指す。

## 4. 各節の調査・執筆

`progress.md` の未完了項目を、前提関係を考慮して順番に処理する。各節について次のサイクルを実行する。

1. **問いの設定**：その節で読者が理解すべきこと、扱う小項目、他節との境界を確認する。
2. **資料収集**：利用可能な検索・閲覧ツールと提供資料を使い、信頼できる出典を探す。学術論文、専門書、一次資料、公式文書、標準仕様、統計の原典を優先し、解説資料・レビューも補助的に使う。重要な主張は可能な限り複数資料で照合する。
3. **記録**：採用した資料を `sources.md` に重複なく登録し、安定した資料ID（`S001` など）、著者・組織、タイトル、公開・更新日、URL/識別子、参照日、種類、留意点を記録する。公開日不明なら不明と書く。
4. **執筆**：用語の定義だけで終えず、なぜ重要か、仕組み・根拠、具体例、他概念との違い、応用、限界まで必要な深さで解説する。数式・図表・コード・具体的事例は理解に役立つ場合に使う。
5. **根拠の紐付け**：検証可能な事実・データ・引用・重要な見解の近くに参照IDと出典リンク（例: `[S003](https://example.org/paper)`）を示す。節末にも「参照資料」を設ける。出典を捏造せず、実際に確認していない情報を確認済みとして扱わない。
6. **品質確認**：主要な疑問に答えているか、見出しに対して記述が浅すぎないか、事実と解釈を区別しているか、引用・リンク・他節との整合が取れているか点検する。
7. **保存・進捗更新**：まず本文ファイルを保存する。内容・出典・構成を確認できた節だけ `progress.md` のチェックを `[x]` に変える。未完了なら `[ ]` のまま、調査済み事項と次の手順を記す。

説明は単なる箇条書きの羅列にせず、まとまった文章で読み進められる水準を目指す。章ごとに適切な深さを選び、既知の説明を機械的に繰り返さない。

## 5. 出典・不確実性のルール

- 参考資料の優先順位はトピックに応じて判断する。一次資料が有力でも、体系化には良質なレビューや専門書が有用な場合がある。
- 発表年と対象時点を区別する。法令・規格・製品仕様・研究動向など更新されうる情報は、可能な範囲で最新版と確認日を明記する。
- 定説と仮説、学術的合意と少数説、事実と著者の推論、相関と因果を混同しない。見解が対立する場合は双方の根拠と未解決点を書く。
- 出典のリンクを並べただけにせず、本文のどの主張を支えるか分かるようにする。二次情報しか確認できない場合はその制約を明記する。
- 検索・外部閲覧が利用できない場合、出典確認が必要な箇所は `要検証` と明記し、`progress.md` に残す。推測で埋めて完成扱いにしない。
- 資料本文の大量転載を避け、要約・比較・独自の構成で説明する。引用は短く明確に区別する。

## 6. 進捗管理と中断耐性

`progress.md` は必ず次の情報を含める。

- **プロジェクト情報**：テーマ、保存先、最終更新日、全体の進行状況。
- **全体チェックリスト**：スコープ設定、目次作成、目次レビュー、全節執筆、出典・リンクの総点検、最終完成。
- **節別チェックリスト**：`- [ ] 01.01 節名 — chapters/01/01-01.md` という形式で全節を列挙。本文・根拠・品質確認が完了したときだけ `[x]` にする。
- **現在の作業**：節ID、進行段階（資料収集中・執筆中・検証中など）、次の具体的な一手。
- **引き継ぎメモ**：見つかった資料、保留中の疑問、要検証箇所、手戻りを避けるための注意点。
- **変更履歴**：目次の重要な改訂、節の分割・統合、調査方針の変更。

次のタイミングで `progress.md` を更新する。

- 目次と初期チェックリストを作成した直後。
- 各節を保存・完了した直後。
- 節の途中で作業が止まりそうなとき、またはセッション終了前。
- 目次やスコープを変更したとき。

長い節を途中で止める場合も執筆済みMarkdownは保存し、冒頭に `> 執筆途中：未検証の箇所あり` と明記する。`progress.md` には残りの小項目、利用済み資料ID、次に確認する論点を具体的に記す。

**可能な限り目次だけで終了せず、本文を順次完成させる。** ただし時間・コンテキスト・ツールの制約で全体を終えられない場合は、無理に完成扱いせず、ファイルと進捗を整えて確実に再開できる状態で区切る。

## 7. ファイルごとの記述要件

### `index.md`

タイトル、調査目的、対象読者、スコープ、基準日、`outline.md` / `progress.md` / `sources.md` へのリンク、完成済みの章・節への導線を含める。

### `outline.md`

書籍風の階層的な全体目次を記す。各節に固有IDを与える。完成済みの節には対応する本文への相対リンクを付ける。未作成節は文字列のままにする。必要なら末尾に「対象外とした論点」とその理由を記す。

### `chapters/NN/NN-MM.md`

以下を基本形とし、テーマに不要な見出しは調整してよい。

```markdown
# 2.3 節名

## この節で学ぶこと
（位置付け・主な問い）

## 2.3.1 基本概念と背景
（定義、前提、なぜ重要か）

## 2.3.2 仕組み・主要な論点
（根拠、理論、分類、関係性）

## 2.3.3 具体例・応用
（理解を助ける例）

## 2.3.4 限界・論争点
（適用条件、反例、未解決課題）

## まとめ
（重要事項と次に読む節への接続）

## 参照資料
- [S001] 著者・組織『資料名』（発表年）: https://example.org/
```

### `sources.md`

ID、著者・組織、資料名、公開・更新日、URL/DOI等、参照日、資料の種類・信頼性上の注意を記録する。新しい節で同じ資料を使うときは既存IDを再利用する。

### `progress.md` の初期形

```markdown
# 調査進捗

- テーマ: ...
- 最終更新: YYYY-MM-DD
- 完了: 0 / N 節
- 現在の作業: 01.01 / 資料収集中
- 次の具体的な作業: 01.01 の主要な一次資料を探す

## 全体チェックリスト
- [x] 調査範囲・想定読者を定義する
- [x] 全体目次を作成する
- [ ] 目次の重複・欠落を点検する
- [ ] すべての節を執筆・検証する
- [ ] 出典・内部リンク・全体の整合を最終確認する

## 節別チェックリスト
- [ ] 01.01 節名 — chapters/01/01-01.md
- [ ] 01.02 節名 — chapters/01/01-02.md
- [ ] 02.01 節名 — chapters/02/02-01.md

## 引き継ぎメモ
- 調査済み: ...
- 未確認・要検証: ...
- 次回の注意点: ...

## 変更履歴
- YYYY-MM-DD: 初期目次を作成
```

## 8. 最終レビューと終了時の報告

- 目次の各節とチェックリストと実ファイルが一対一に対応するか確認する。
- 節間の重複、概念定義の矛盾、古い情報、典拠不明の重要主張、欠落、壊れた相対リンクを確認する。
- 重要な未検証事項が残る場合は完成と表記せず、どこが暫定的か分かるようにする。
- ユーザーには保存先、完了節数/全節数、作成した主要ファイル、今回の成果、未了項目と次回の再開位置を短く報告する。
